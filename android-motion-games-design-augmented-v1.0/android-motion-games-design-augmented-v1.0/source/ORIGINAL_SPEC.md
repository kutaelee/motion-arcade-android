# Android 2인 모션 인식 2D 미니게임 제작·설계 원샷 프롬프트

당신은 Android 네이티브 개발, 실시간 컴퓨터 비전, 2D 게임 시스템을 함께 설계하고 구현하는 시니어 엔지니어다.

단순한 기획 문서를 작성하는 데 그치지 말고, 아래 요구사항을 만족하는 실행 가능한 Android 프로젝트를 설계하고 구현하라. 구현 결과는 Android Studio와 Gradle CLI에서 재현 가능해야 하며, 실제 실행하지 않은 테스트나 성능 결과를 성공했다고 표현하지 마라.

---

# 1. 제품 목표

스마트폰의 전면 또는 후면 카메라로 사용자의 전신 또는 상반신 움직임을 인식하여 조작하는 Android 2D 게임 앱을 제작한다.

기본 제공 게임은 다음 3종이다.

1. 낚시 게임
2. 권투 격투 게임
3. 몬스터 사냥 및 보스 협동 게임

모든 게임은 다음 모드를 지원해야 한다.

* 솔로 모드: 1인 포즈 인식
* 듀얼 모드: 한 카메라 화면에서 최대 2인 포즈 동시 인식
* 세로 모드
* 가로 모드
* 전면 카메라
* 후면 카메라

게임은 인터넷 연결이나 유료 API 없이 오프라인에서 동작해야 한다.

# 2. 확정된 범위와 가정

## 2.1 확정 범위

* 플랫폼: Android 네이티브
* 언어: Kotlin
* 최소 지원 버전: minSdk 26
* compileSdk와 targetSdk: 구현 시점의 최신 안정 버전을 확인한 후 고정
* 플레이 인원: 1명 또는 2명
* 듀얼 모드: 동일 기기와 동일 카메라 프레임 안에 2명이 함께 들어가는 로컬 플레이
* 카메라: 전면 또는 후면 중 하나를 선택하여 사용
* 포즈 추론: 온디바이스 처리
* 영상 서버 전송: 금지
* 영상 녹화 및 저장: 기본적으로 금지
* 계정, 로그인, 서버, 네트워크 멀티플레이: MVP 범위 제외
* 음성 인식과 마이크 권한: 범위 제외
* 과금, 광고, 가챠, 유료 아이템: 범위 제외

## 2.2 명시적 Non-goals

다음 기능은 구현하지 않는다.

* 전면·후면 카메라 동시 사용
* 서로 다른 기기 간 실시간 멀티플레이
* 실제 펀치 힘이나 운동 강도 측정
* 얼굴 인식 또는 생체 식별
* 원본 카메라 프레임 저장
* 실시간 3D 아바타 모션 캡처
* Unity, Unreal Engine 또는 유료 게임 엔진 사용
* 유료 SDK, 유료 에셋, 유료 API 의존
* 손가락 단위의 정밀 제스처를 필수 게임 입력으로 사용

# 4. 기술 선택 원칙

이 앱은 카메라와 모션 인식이 핵심이므로 게임 엔진보다 Android 카메라 호환성과 포즈 파이프라인의 관측 가능성을 우선한다.

MVP에서는 libGDX, Godot 등의 게임 엔진을 사용하지 않는다.

게임 화면은 다음 방식으로 구현한다.

* 일반 화면과 HUD: Jetpack Compose
* 카메라 미리보기: CameraX `PreviewView`
* 게임 필드: 하드웨어 가속 Android Custom View와 Canvas
* 프레임 스케줄링: Choreographer
* 게임 시뮬레이션: 고정 시간 간격 60Hz
* 렌더링: 시뮬레이션 상태를 보간하여 표시

Canvas 성능이 실제 프로파일링에서 목표를 충족하지 못한 경우에만 렌더러 인터페이스를 유지한 채 OpenGL 또는 libGDX 전환을 ADR로 제안한다. 사전 최적화 목적으로 엔진을 추가하지 않는다.

# 6. 핵심 데이터 흐름

다음 의존 방향을 유지한다.

```text
CameraX ImageAnalysis
    ↓
PoseLandmarkerAdapter
    ↓
RawPoseFrame
    ↓
PoseCoordinateTransformer
    ↓
NormalizedPoseFrame
    ↓
PlayerTracker
    ↓
MotionFeatureExtractor
    ↓
GestureStateMachine
    ↓
MotionEvent
    ↓
GameSession
    ↓
GameSnapshot
    ↓
CanvasRenderer
```

게임 코드는 MediaPipe 클래스나 카메라 프레임을 직접 참조하면 안 된다.

게임에 전달되는 입력은 다음과 같은 의미 기반 이벤트여야 한다.

```kotlin
data class MotionEvent(
    val playerId: PlayerId,
    val type: MotionType,
    val quality: Float,
    val confidence: Float,
    val timestampMs: Long,
    val metadata: Map<String, Float>
)
```

예:

```text
PUNCH_JAB
PUNCH_HOOK
DODGE_LEFT
FISH_CAST
FISH_REEL_CYCLE
MONSTER_BLOCK
TEAM_ULTIMATE
```

# 7. 카메라 처리

## 7.1 CameraX 구성

* `Preview`와 `ImageAnalysis`를 동시에 바인딩한다.
* `ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST`를 사용한다.
* 분석 해상도 초기값은 640×480 또는 기기 비율에 맞는 근접 해상도로 한다.
* 성능이 충분한 기기에서만 720p 분석을 허용한다.
* ML 추론은 메인 스레드에서 실행하지 않는다.
* `ImageProxy`는 성공·실패 여부와 관계없이 `finally`에서 닫는다.
* 앱이 백그라운드로 가면 카메라와 추론을 중지한다.
* 카메라 전환 시 게임을 일시정지하고 재캘리브레이션한다.

## 7.2 화면 회전

세로·가로 회전 시 다음을 보장한다.

* 게임 점수 유지
* 타이머 유지
* 보스 체력 유지
* 플레이어 역할 유지
* 카메라 재바인딩
* 포즈 좌표 변환 갱신
* 최대 1초 이내 자동 재개
* 재개 전 3초 카운트다운 제공

회전 과정에서 플레이 세션을 새로 시작하지 않는다.

## 7.3 전면 카메라 미러링

전면 카메라의 미리보기는 거울처럼 표시할 수 있지만 내부 좌표는 정규화된 canonical 좌표로 변환한다.

다음 개념을 분리한다.

* 해부학적 좌우
* 카메라 센서 좌표
* 화면 표시 좌표
* 전면 카메라 미러 좌표
* 게임 월드 좌표

게임 규칙에서 카메라 렌즈에 따라 왼쪽과 오른쪽이 반전되면 안 된다.

# 8. 2인 플레이어 추적

얼굴 인식이나 외형 식별을 사용하지 않는다.

## 8.1 초기 배정

캘리브레이션 시 골반 중심의 X 좌표를 기준으로 배정한다.

* 화면 왼쪽 사람: Player 1
* 화면 오른쪽 사람: Player 2

## 8.2 지속 추적

매 프레임 단순 X 정렬만 다시 수행하지 않는다.

다음 특징을 이용해 이전 프레임과 현재 프레임을 매칭한다.

* 골반 중심 위치
* 어깨 중심 위치
* 이동 속도
* 신체 크기
* 이전 프레임과의 거리
* 이동 방향 연속성

2명뿐이므로 최소 비용 매칭을 직접 구현한다.

## 8.3 교차와 가림 처리

* 플레이어별 화면 레인을 표시한다.
* 플레이어가 레인을 교차하면 경고한다.
* 두 사람의 바운딩 박스가 과도하게 겹치면 게임을 일시정지한다.
* ID가 불확실한 상태에서 임의로 역할을 교환하지 않는다.
* 재인식 시 중립 자세를 1초 유지하고 재배정한다.
* 한 명이 1.2초 이상 사라지면 듀얼 게임을 일시정지한다.
* 한 명만 감지되더라도 다른 플레이어의 캐릭터를 자동 조작하지 않는다.

# 9. 포즈 정규화

원본 좌표에 직접 임계값을 적용하지 않는다.

다음 순서로 정규화한다.

1. 관절 신뢰도 필터
2. 카메라 회전 보정
3. 전면 카메라 미러 보정
4. 골반 중심을 원점으로 변환
5. 어깨 폭과 몸통 길이를 기준으로 크기 정규화
6. EMA 또는 One Euro Filter 방식의 평활화
7. 최근 5~10프레임 기반 속도와 가속도 계산

주요 기준값:

* 관절 기본 신뢰도 기준: 0.55
* 필수 관절 중 2개 이상 신뢰도 미달 시 해당 동작 판정 금지
* 400ms 이내 일시 손실: 이전 값을 제한적으로 유지
* 1.2초 이상 손실: 플레이 일시정지
* 순간적인 한 프레임 판정으로 액션을 발생시키지 않음

# 10. 동작 인식 엔진

모든 동작은 시간 상태 머신으로 구현한다.

```text
IDLE
→ CANDIDATE
→ CONFIRMED
→ COOLDOWN
→ IDLE
```

각 동작은 다음 항목을 가진 데이터 기반 설정으로 정의한다.

```text
gestureId
requiredLandmarks
entryConditions
progressConditions
confirmationConditions
cancelConditions
minimumDurationMs
maximumDurationMs
cooldownMs
qualityWeights
```

설정 파일 예:

```text
assets/config/gesture_defaults.json
```

초기 임계값은 하드코딩하지 말고 JSON 또는 Kotlin 설정 객체로 분리한다.

## 10.1 동작 품질 점수

모든 성공 동작은 0.0~1.0 사이 품질 점수를 생성한다.

```text
quality =
    timingAccuracy × 0.40
  + poseForm × 0.30
  + normalizedRange × 0.20
  + stability × 0.10
```

속도는 안전 상한을 적용하며 무조건 빠를수록 높은 점수를 주지 않는다.

## 10.2 오인식 방지

* 동작별 cooldown 적용
* 반대 방향 이동이 없는 단순 손 떨림 무시
* 몸 전체 이동과 팔 동작을 분리
* 동작 완료 전 방향이 반전되면 취소
* 중립 상태에서 반복 발생하는 이벤트 측정
* 인식 신뢰도가 낮으면 보상을 주지 않음
* 여러 동작이 동시에 후보가 되면 우선순위와 상호 배제 규칙 적용

# 11. 공통 캘리브레이션

게임 시작 전 5~8초 캘리브레이션을 제공한다.

순서:

1. 카메라에 전신 또는 필요한 상반신이 들어오는지 확인
2. 정면 중립 자세 2초
3. 팔을 좌우로 펼쳐 신체 스케일 측정
4. 양손을 들고 플레이어 확인
5. 듀얼 모드에서는 P1과 P2 레인 확인
6. 조명과 관절 신뢰도 확인
7. 게임별 핵심 동작 1회 연습

캘리브레이션 실패 사유를 구체적으로 표시한다.

* 몸이 너무 가까움
* 몸이 너무 멂
* 머리 또는 손이 화면 밖
* 조명이 부족함
* 두 플레이어가 겹침
* 한 명만 감지됨
* 카메라 권한 없음
* 기기 성능 부족

```text
→ 릴 감기
→ 장력 조절
→ 뜰채 또는 포획
→ 결과
```

솔로 모드에서는 모든 단계를 한 명이 수행한다.

듀얼 모드 역할:

* Player 1: 낚싯대 담당
* Player 2: 장력 보조 및 뜰채 담당
* 물고기를 잡을 때마다 역할 교대 가능
* 한 플레이어가 실패해도 즉시 전체 실패시키지 않고 회복 기회를 제공

## 12.2 인식 동작

| 동작       | 인식 조건                         | 게임 효과     |
| -------- | ----------------------------- | --------- |
| 준비       | 손을 가슴 근처에 두고 500ms 안정         | 캐스팅 준비    |
| 캐스팅      | 손이 어깨 뒤·위에서 전방으로 이동하고 팔꿈치가 펴짐 | 찌 투척      |
| 챔질       | 입질 시간창 안에 손목 또는 팔을 빠르게 위로 당김  | 물고기 걸기    |
| 릴 감기     | 손 중심이 가슴 앞에서 반복적인 원형 또는 교대 운동 | 물고기 끌어오기  |
| 좌우 장력 조절 | 어깨 중심이 골반 중심 대비 좌우로 기울어짐      | 줄 장력 조정   |
| 뜰채       | 양손을 낮췄다가 위로 퍼 올리는 동작          | 물고기 최종 포획 |

초기 튜닝 기준:

* 캐스팅 손목 이동량: 어깨 폭의 0.45 이상
* 캐스팅 최대 시간: 700ms
* 챔질 상승량: 몸통 길이의 0.25 이상
* 챔질 최대 시간: 350ms
* 릴 1회전 판정: 누적 각도 약 240도 이상
* 장력 조절은 몸 전체 이동이 아니라 상체 기울기를 우선 사용

손 세부 인식이 불안정하면 릴 동작을 팔꿈치 굽힘·펴기 반복으로 대체한다.

## 12.3 보상

보상은 다음으로 계산한다.

* 캐스팅 정확도
* 챔질 타이밍
* 릴 리듬 유지
* 장력 안정성
* 협동 성공률
* 연속 포획 콤보
* 물고기 희귀도

캐스팅 거리는 팔 속도가 아니라 동작 범위와 타이밍으로 결정한다.

희귀 물고기는 순수 랜덤이 아니라 다음 조합으로 결정한다.

```text
기술 점수 + 지역 난이도 + 시드 기반 랜덤 + 연속 실패 보정
```

초기 콘텐츠:

* 낚시터 1개
* 일반 물고기 4종
* 희귀 물고기 2종
* 보스 물고기 1종
* 날씨 또는 시간대 배경 변형 2종

# 13. 게임 2: 권투 격투

## 13.1 게임 구조

솔로 모드:

* 플레이어 대 AI 복서
* 3라운드 또는 간소화된 90초 경기
* AI는 공격 전 시각적 예고를 제공
* 난이도에 따라 예고 시간과 방어 빈도를 조정

듀얼 모드:

* 두 플레이어가 화면 좌우 레인에 선다.
* 실제로 서로를 향해 주먹을 뻗지 않고 카메라 방향으로 섀도 복싱한다.
* 각 플레이어의 동작이 화면 속 복서에 적용된다.
* 플레이어 간 물리 접촉을 유도하지 않는다.
* 레인 침범 시 게임을 일시정지한다.

## 13.2 인식 동작

| 동작    | 인식 조건                       | 게임 효과    |
| ----- | --------------------------- | -------- |
| 가드    | 양 손목이 얼굴 근처, 팔꿈치가 몸통 근처     | 얼굴 방어    |
| 잽     | 앞손이 짧게 전진하고 팔꿈치가 빠르게 펴짐     | 빠른 공격    |
| 스트레이트 | 뒷손이 전진하고 어깨 회전이 동반됨         | 중간 공격    |
| 훅     | 팔꿈치를 굽힌 상태에서 손목이 몸통 앞을 가로지름 | 측면 공격    |
| 어퍼컷   | 허리 부근 손목이 턱 방향으로 상승         | 하단 공격    |
| 좌우 회피 | 머리·어깨 중심이 골반 대비 좌우 이동       | 공격 회피    |
| 덕킹    | 어깨와 골반 높이가 낮아지고 무릎이 굽음      | 상단 공격 회피 |
| 바디 블록 | 팔을 몸통 앞에 모음                 | 몸통 방어    |

초기 튜닝 기준:

* 잽·스트레이트 손목 이동량: 어깨 폭의 0.35 이상
* 펀치 판정 시간: 250~450ms
* 펀치 전후 팔꿈치 각도 변화 필수
* 훅은 팔꿈치 각도 70~130도 범위 유지
* 회피는 코 중심 이동량 어깨 폭의 0.20 이상
* 덕킹은 어깨 중심 높이 몸통 길이의 0.18 이상 하강
* 펀치 cooldown: 350~500ms
* 같은 손 연속 입력에는 체력 비용 증가

## 13.3 피해와 보상

피해량은 실제 힘이 아니라 다음으로 결정한다.

```text
기본 공격력
```

* 무작위 팔 휘두르기
* 같은 동작 연타
* 가드 없이 공격만 반복
* 레인 이탈
* 상대 플레이어와 물리적으로 가까워짐

보상 요소:

* 유효타
* 정확한 방어
* 카운터 타이밍
* 콤보 다양성
* 체력 관리
* 라운드 승리
* 무피격 보너스

초기 콘텐츠:

* 경기장 1개
* 난이도 3단계
* 튜토리얼 훈련 모드
* 듀얼 대전 모드

# 14. 게임 3: 몬스터 및 보스 협동

## 14.1 게임 구조

2D 횡스크롤 또는 단일 화면 아레나 방식으로 구현한다.

기본 진행:

```text
일반 몬스터 웨이브
→ 엘리트 몬스터
→ 보스 등장
→ 보스 페이즈 전환
→ 협동 필살기
→ 결과
```

솔로 모드:

* 플레이어 1명
* 단순 AI 동료 1명 제공
* AI는 이동, 기본 공격, 위험 회피만 수행
* 플레이어 핵심 행동을 대신하지 않음

듀얼 모드:

* Player 1: Vanguard 역할
* Player 2: Ranger 또는 Mage 역할
* 역할별 동작 세트를 일부 다르게 제공
* 한 명이 쓰러지면 다른 플레이어가 부활 동작 수행
* 보스 약점 구간에서 협동 동작 제공

## 14.2 공통 동작

| 동작     | 인식 조건                    | 게임 효과       |
| ------ | ------------------------ | ----------- |
| 기본 공격  | 손목이 몸 앞을 빠르게 가로지르는 동작    | 검 또는 원거리 공격 |
| 강공격    | 양손을 머리 위에 유지한 뒤 아래로 내림   | 큰 피해        |
| 방어     | 양팔을 가슴 앞에서 교차            | 피해 감소       |
| 좌우 회피  | 상체가 좌우로 빠르게 이동           | 공격 회피       |
| 마법 충전  | 양팔을 V자로 들어 일정 시간 유지      | 스킬 게이지 충전   |
| 스킬 발동  | 충전 후 양손을 앞으로 내밈          | 클래스 스킬      |
| 부활     | 쓰러진 동료 방향으로 양팔을 뻗고 유지    | 동료 부활       |
| 협동 필살기 | 두 플레이어가 제한 시간 내 지정 자세 수행 | 팀 필살기       |

초기 튜닝 기준:

* 기본 공격 이동량: 어깨 폭의 0.40 이상
* 강공격 시작: 양 손목이 머리보다 위에서 500ms 유지
* 강공격 종료: 몸통 길이의 0.50 이상 하강
* 방어 자세: 양 손목 간 거리와 팔 교차 여부 확인
* 마법 충전: 팔 V 자세 800ms 유지
* 부활: 지정 방향으로 팔을 1.5초 유지
* 협동 필살기 동기화 허용 오차: 600ms

## 14.3 보스 설계

보스는 최소 3개 페이즈를 가진다.

### 페이즈 1

* 단순한 예고 공격
* 기본 회피와 방어 학습
* 약점 노출 시간 길게 제공

### 페이즈 2

* 좌우 범위 공격
* 역할 분담 필요
* 한 플레이어가 방어하고 다른 플레이어가 공격

### 페이즈 3

* 협동 필살기 게이지 활성화
* 두 플레이어가 동기화 동작 수행
* 실패해도 즉사시키지 않고 재도전 기회 제공

## 14.4 보상

* 개인 동작 품질
* 팀 피해량
* 방어 성공
* 동료 구조
* 역할 수행
* 협동 동기화 정확도
* 보스 클리어 시간
* 남은 팀 체력

개인 점수와 팀 점수를 모두 제공한다.

초기 콘텐츠:

* 일반 몬스터 3종
* 엘리트 몬스터 1종
* 보스 1종

* 협동 필살기 연출

## 19.3 에셋 방식

ImageGen 결과의 프레임 간 일관성 문제를 줄이기 위해 다음을 우선한다.

* 캐릭터를 정적인 레이어 파츠로 생성
* 머리, 몸통, 팔, 무기, 효과를 분리
* 런타임에서 회전·이동·스케일 tween 적용
* 복잡한 전신 프레임 애니메이션을 과도하게 생성하지 않음
* 필수 액션만 4~8프레임 키 애니메이션으로 생성

각 에셋은 다음 정보를 가진다.

```text
assetId
gameId
sourcePrompt
sourceFile
processedFile
width
height
pivotX
pivotY
collisionBounds
licenseOrProvenance
generationDate
revision
```

다음 파일을 생성한다.

```text
docs/assets/art-direction.md
docs/assets/imagegen-prompts.md
docs/assets/asset-manifest.json
scripts/process-assets.*
```

ImageGen을 직접 실행할 수 없는 환경에서는 임시 도형과 placeholder를 사용해 기능을 완성하고, 필요한 생성 프롬프트를 문서화한다.

에셋 부재 때문에 핵심 로직 구현을 중단하지 않는다.

# 21. 성능 목표

렌더링과 ML 추론 속도를 분리해 측정한다.

## 21.1 렌더링

* 목표 평균 FPS: 60
* P90 프레임 시간: 20ms 이하
* P99 프레임 시간: 33ms 이하
* 짧은 정지나 회전 중 프레임은 별도 구분
* 평균 FPS만으로 성공 판정 금지

## 21.2 포즈 추론

중급 Android 기기 기준:

* 솔로 추론: 20 FPS 이상 목표
* 듀얼 추론: 15 FPS 이상 목표
* 동작 발생부터 게임 반응까지 P95 180ms 이하
* 분석 큐 누적 금지
* 오래된 프레임은 폐기

## 21.3 성능 적응

성능 저하 또는 발열 시 다음 순서로 축소한다.

1. 포즈 추론 빈도 감소
2. 분석 해상도 감소
3. 파티클 수 감소
4. 카메라 미리보기 해상도 감소
5. Hand Landmarker 비활성화
6. 그림자와 후처리 효과 비활성화

게임 시뮬레이션 속도나 판정 시간창을 기기 성능에 따라 변경하지 않는다.

## 23.1 단위 테스트

* 보스 페이즈
* 시드 기반 보상
* 세션 저장과 복원

## 23.2 포즈 fixture

원본 영상에 의존하지 않는 `PoseFrame` 시퀀스 fixture를 만든다.

각 동작마다 최소 다음 fixture를 제공한다.

* 정상 동작
* 너무 느린 동작
* 너무 작은 동작
* 반대 방향 동작
* 중간 취소
* 낮은 신뢰도
* 다른 동작과 혼동되는 사례
* 중립 움직임
* 2인 동시 동작

초기 smoke gate:

* 동작당 positive 10개 이상
* 동작당 negative 10개 이상

릴리스 gate:

* 동작당 positive 30개 이상
* 동작당 negative 30개 이상
* 다양한 신장, 옷, 조명, 배경 조건 포함

## 23.3 인식 품질 기준

릴리스 후보 기준:

* 핵심 동작 precision 0.90 이상
* 핵심 동작 recall 0.85 이상
* 중립 상태 오발생: 60초당 1회 미만
* 듀얼 레인 미교차 상황에서 플레이어 ID 교환 0회
* 레인 교차 시 임의 ID 교환 대신 안전 일시정지
* 인식 실패 시 게임 상태가 잘못 진행되지 않음

기준을 충족하지 못한 동작은 제거하거나 입력 방식을 단순화한다.

## 23.4 Android 계측 테스트

다음 조합을 테스트한다.

```text
세로 × 전면 × 솔로
세로 × 후면 × 솔로
가로 × 전면 × 솔로
가로 × 후면 × 솔로
세로 × 전면 × 듀얼
세로 × 후면 × 듀얼
가로 × 전면 × 듀얼
가로 × 후면 × 듀얼
```

추가 조건:

* 카메라 권한 거부
* 권한 영구 거부
* 카메라 없는 에뮬레이터
* 앱 백그라운드 전환
* 전화나 알림에 의한 중단
* 회전 중 플레이
* 한 명이 화면 밖으로 이동
* 조명 저하
* 두 명이 겹침
* 앱 프로세스 재생성
